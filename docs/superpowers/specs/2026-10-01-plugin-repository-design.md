# Plugin repository and in-app catalog

Tracks phase 5 of [#1560](https://github.com/mrmans0n/alas/issues/1560):
distribution and discovery.

## Goal

One GitHub repository, `mrmans0n/alas-plugins`, holds the source of every
plugin people can use. Alas lists its plugins in **Settings → Plugins** and installs,
updates and removes them without a terminal. Loading a plugin from a local
folder keeps working as it does today.

## Decisions

- **One public monorepo for plugin source.** First-party plugins (Kanban,
  Pixel Office) and community plugins live side by side. Contributing a plugin
  means opening a PR there. Review of that PR is the curation step.
- **The Rust SDK moves with them.** `plugins/alas-plugin` becomes
  `alas-plugins/sdk/alas-plugin`. The plugins depend on it by path, so an SDK
  change and the plugins it affects land in one PR.
- **The contract stays in Alas.** The host owns the API, so `docs/plugins/api-v*.md`,
  `concepts.md` and `troubleshooting.md` stay here. `plugins/samples/hello-workspace`
  stays too, as the smallest test of the host. It is plain JavaScript with no SDK.
- **No archives.** A plugin is two files, `plugin.json` and `plugin.js`. A
  release publishes both as assets, so Alas can install a plugin without
  unzipping anything.
- **One hash.** The index records `PluginTrust.hash(manifest:entry:)`, the same
  value approvals use. Alas verifies the downloaded files against it, and the
  existing approval flow does the rest.

## Repository layout

```
alas-plugins/
├── sdk/alas/                 # the TypeScript SDK plugins depend on
├── plugins/
│   ├── kanban/               # package.json, plugin.json, src/, README.md
│   └── pixel-office/
├── scripts/
│   ├── jsc-run               # runs a built plugin.js in a bare JavaScriptCore context
│   └── trust-hash            # computes PluginTrust's hash for the index
├── index.json                # generated by CI; never edited by hand
└── .github/workflows/
    ├── ci.yml                # every PR: typecheck, node --test, esbuild build per plugin
    └── release.yml           # on tag <folder>-v<version>: build, publish, update index.json
```

## Index format

Served from `https://raw.githubusercontent.com/mrmans0n/alas-plugins/main/index.json`.

```json
{
  "format": 1,
  "plugins": [{
    "id": "io.nlopez.kanban",
    "name": "Kanban",
    "summary": "A ticket board whose tickets start agent tasks.",
    "homepage": "https://github.com/mrmans0n/alas-plugins/tree/main/plugins/kanban",
    "versions": [{
      "version": "0.3.0",
      "api": 4,
      "capabilities": ["workspace.read", "session.focus", "session.read", "tasks.start"],
      "manifest": "https://github.com/mrmans0n/alas-plugins/releases/download/kanban-v0.3.0/plugin.json",
      "entry": "https://github.com/mrmans0n/alas-plugins/releases/download/kanban-v0.3.0/plugin.js",
      "hash": "<PluginTrust hash>"
    }]
  }]
}
```

- `versions` keeps every release, newest first. Alas shows the newest version
  whose `api` it supports, so an older Alas still gets something that loads.
- `capabilities` is copied from the manifest so the list can show what a plugin
  asks for before downloading anything.
- `summary` comes from a new optional manifest field. Older versions of Alas
  ignore unknown manifest fields, so adding it does not need an API bump.
  `homepage` is the plugin's folder in the repo.
- Alas ignores a `format` it does not know and shows "Catalog needs a newer Alas".

## Release pipeline

1. Bump `version` in the plugin's `plugin.json` and `package.json`, then merge.
2. Push the tag `kanban-v0.3.0`.
3. `release.yml` bundles `plugin.js` with esbuild, checks that the tag matches the manifest
   version, creates the GitHub release with both files, computes the hash, adds
   the entry to `index.json` and pushes it to `main`.

Community plugins use the same tag scheme. Only maintainers push tags, so
merging a PR does not publish it.

## Alas: catalog in Settings → Plugins

- An **Available** section below the installed list. Alas fetches the index when
  the pane opens, at most once every 10 minutes, and always on **Refresh**. Each
  row shows the name, version, summary, and the capabilities written out in
  words, with an **Install** button.
- **Install** downloads both files, verifies the hash, and writes them to
  `Plugins/.staging/<id>/`. Discovery skips hidden entries, so the staging folder
  is never scanned as a plugin. Install then moves that folder to `Plugins/<id>/`
  and rescans the plugins folder. The plugin shows up unapproved and goes through the
  existing **Approve…** sheet. Nothing runs before the user approves it.
- **Update available** appears on an installed plugin when the index has a newer
  compatible version for its id. Updating downloads, verifies and stages the new
  files the same way while the old version keeps running. Only once that worked
  does it stop the plugin's instances and swap the folder in with
  `FileManager.replaceItemAt(_:withItemAt:)`, which replaces it in one step, then
  rescan. A failed update leaves the installed version running. Because the hash changed, the plugin asks
  for approval again, which is the right moment to review any new capabilities.
- **Remove** is offered for plugins installed from the catalog (folder name is
  the id and the hash matches some catalog version). It stops the instances and
  deletes the folder. Approvals and storage stay, so reinstalling keeps the
  plugin's data. Clearing data stays a separate action.
- A locally built plugin with the same id in another folder wins. Discovery
  treats a duplicate id specially when exactly one copy sits in the catalog's
  `Plugins/<id>` folder: the other copy loads, and the catalog copy is listed
  under Not loaded as shadowed. Any other duplicate still quarantines every copy.
  The catalog row then says "Installed locally" and offers no Install or Update.
- Network failures, a bad hash, or a malformed index show one line in the
  section and never touch installed plugins.

Behind the existing experimental Plugins setting, like the rest of the system.

## Migration

1. Create `alas-plugins` with the SDK, Kanban and Pixel Office, their history
   kept via `git filter-repo` on `plugins/`.
2. Publish the first releases so the index has entries.
3. In Alas, delete `plugins/alas-plugin`, `plugins/kanban` and
   `plugins/pixel-office`, their rows in the Rust job of
   `.github/workflows/build.yml`, and the matching
   `scripts/tests/ci-workflow/test-build-workflow.rb` expectations. Point
   `hello-workspace` at the SDK tag. Update `docs/plugins/` links.

## What community plugins will need next (not in this spec)

The plugins the repo is meant to attract, such as Notion, Linear or GitHub
integrations, need host APIs that do not exist yet. They are specced in
`2026-10-01-plugin-api-expansion-design.md`, starting at API 5 (API 4 is the
JavaScript runtime switch):

- **`http.fetch` with a host allowlist** declared in the manifest and shown in
  the approval sheet. Alas makes the request, so the plugin never gets sockets.
- **Secrets.** The user enters the API token in Settings. Alas keeps it in the
  Keychain and attaches it to allowed requests, so the plugin never sees it.
- **Timers or polling.** Plugins are passive today, so syncing Linear issues needs
  Alas to wake the plugin on an interval it declares.
- **Task completion events**, so a Linear bridge can move its issue when the
  agent's worktree is merged.

## Out of scope

Signing beyond the hash, third-party catalogs, search, ratings, automatic
updates, and paid plugins.

## Testing

- **Alas:** one suite for the catalog logic as plain functions: version selection
  by supported API, hash verification, and the installed/update/local-wins state of
  a row. Install and update tested once against a temporary plugins folder,
  with downloads served from an in-memory fake.
- **alas-plugins:** `node --test` for each plugin. `scripts/trust-hash` hashes
  `"alas-plugin-trust-v1\0" + manifest + "\0" + entry`. A fixture pair and its
  expected hash are checked in to both repos, so either side drifting fails its
  own CI.
